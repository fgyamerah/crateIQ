# Reconciliation Reference-Artifact Design

**Status:** Stages 1–3 implemented; Stage 4 apply/rollback remains future work
**Date:** 2026-08-11
**Scope:** detecting, classifying, planning, reviewing, and correcting stale queue/reference artifacts

---

## 1. Scope Boundary

"Queue/reference artifact reconciliation" means detecting and correcting references
that have become **stale because an underlying track identity changed** (path
renamed, track row deleted, or track promoted to a different storage zone), without
moving, renaming, quarantining, deleting, or rewriting any audio file, tag, or
MIK-authoritative BPM/key/cue.

### In scope

- Detecting stale references in mutable, correctable surfaces that reference
  tracks by path or by track ID where the track row itself may be gone or
  superseded.
- Classifying those references into fixable, review-required, regenerable,
  historical/immutable, and disposable/ignore categories.
- Proposing precise, reversible correction plans.
- (Future) human review, revalidation, narrow apply, and verified rollback of
  individual corrections to reference artifacts.

### Explicitly NOT in scope

- Moving, renaming, or deleting audio files or directories.
- Quarantining audio files.
- Rewriting media tags (ID3, FLAC, etc.).
- Altering MIK-authoritative BPM/key/cue data.
- Broad filesystem cleanup.
- Applying duplicate resolution (filesystem or DB).
- Silently repairing every historical path string.
- Changing reconciliation_ledger rows (immutable append-only history).

### Separation from current DB-only reconciliation

The current Phase 1 DB-only reconciliation (`update_path_reference` on
`tracks.filepath` and `mark_stale_processed_state_path` on `processed_state`)
covers exactly two target tables in `processed.db`. This is deliberate:
`tracks` is the canonical current-state path authority, and `processed_state`
is the processing-stage history that becomes stale when a track path moves.

**This reference-artifact phase explicitly does not reopen or broaden the
`processed.db` apply scope.** `tracks` and `processed_state` remain the
exclusive current DB-only apply surfaces. The new phase covers everything else
that references a track identity.

## 3. Classification of Artifact Types

Every artifact falls into exactly one of these five categories for
reconciliation purposes:

### Category A — Immutable historical provenance (never rewrite)

- `track_history.filepath`, `track_history.original_path`
- `duplicate_groups.original`, `duplicate_groups.duplicate`
- `reconciliation_ledger` (all rows)
- `pipeline_runs`
- `tag_write_operations` (all rows — immutable operational provenance: plan, backup manifest, and result JSON are point-in-time evidence of a controlled tag-write operation and its verified backup/restore state)
- `field_provenance` rows where `is_current = 0`
- `track_history.rolled_back` rows

**Rule:** These must remain exactly as written. Their value is as
point-in-time evidence, not as navigable references. Stale paths in these
tables are a feature, not a bug.

### Category B — Mutable authoritative/reference state (correct carefully)

- `cue_points.filepath`
- `set_playlist_tracks.filepath`
- `manual_crate_tracks.track_id` (only when track was deleted; re-attach to
  the replacement track row if proven)
- `field_provenance` rows where `is_current = 1`
- Queue JSON/JSONL entries that are mutable operational state (not review
  snapshots dated to a specific review cycle)

**Rule:** These can be corrected with a precise, reviewed, verified,
rollback-capable mutation. Each correction must carry exact before/after
values, provenance, and a backup or rollback path.

### Category C — Review state (snapshot-scoped; expire or re-derive)

- `metadata_repair_queue` (regenerated on `refresh()` — stale entries
  should trigger regeneration, not individual field patching)
- `enrichment_review_snapshots` / `_decisions`
- `beets_review_snapshots` / `_decisions`
- `duplicate_review_snapshots` / `_decisions`
- `quality_review_snapshots` / `_decisions`
- `quality_review_findings` (durable findings — persist orphaned track_ids
  as evidence but mark them as unresolvable)
- `track_reviews` (orphaned track_id when track deleted; invisible in
  read queries since LEFT JOIN requires a tracks row — flag as orphaned)
- `genre_review_snapshots` (orphaned track_ids in items_json blob;
  flagged for regeneration like other review snapshots)
- `bpm_anomalies`

**Rule:** Review state is tied to a specific snapshot. A stale reference
should trigger detection (flag the item for re-review or regeneration)
rather than surgically patching individual entries inside a JSON blob that
was frozen at review time. `metadata_repair_queue` is already regenerated
by `refresh()`, so orchestrate regeneration rather than field-level edits.
For durable findings (`quality_review_findings`), mark orphaned rows as
unresolvable rather than deleting or rewriting them.

### Category D — Regenerable derived artifacts (re-export, do not mutate)

- M3U8/JSON/CSV/XML export files
- Staged Serato M3U8 + manifest

**Rule:** The source of truth is the current processed.db tracks + crate
state. Export output that references a stale path should be flagged for
re-export, not parsed and surgically patched.

### Category E — Disposable cache / operational state (ignore or prune)

- `waveform_track_state` (stale track_ids should be pruned by the cache
  lifecycle manager, not by reconciliation)
- `waveform_jobs` terminal rows
- `bpm_retry_pauses` (orphaned track_id when track deleted; no meaning
  without a surviving track — prune)
- `track_fingerprints` (orphaned track_id when track deleted; optional
  corroborating evidence with no surviving track — prune)
- Waveform cache files on disk

**Note:** `metadata_lookup_cache` is **not** included in Category E
scanning. It is keyed on (artist, title) — not track ID or path — so it
cannot become stale through reference reconciliation. It is listed in the
inventory at #34 for completeness only and should never be scanned or emit a
reference finding.

**Rule:** These are disposable by definition. Let cache lifecycle/eviction
handle them. Reconciliation should not spend resources on cache entries.

## 4. Finding Model

A reference-artifact finding is a read-only observation of a stale
reference. It does not propose a fix or authorize mutation.

### Finding fields

| Field | Required | Description |
|-------|----------|-------------|
| `finding_id` | Required | Stable hash-derived ID, e.g., `ref-stale-<hex12>` |
| `artifact_type` | Required | One of: `cue_point`, `playlist_track`, `crate_track`, `repair_queue_item`, `enrichment_review_snapshot`, `beets_review_snapshot`, `duplicate_review_snapshot`, `quality_review_snapshot`, `quality_review_finding`, `track_review`, `genre_review_snapshot`, `field_provenance`, `queue_entry`, `bpm_anomaly`, `bpm_retry_pause`, `fingerprint_cache`, `export_file` |
| `artifact_owner` | Required | Module/service name |
| `artifact_identifier` | Required | Row ID, compound key, or path+index within a JSON blob |
| `reference_field` | Required | E.g., `filepath`, `track_id`, `relative_path`, `original` |
| `stale_value` | Required | The current (stale) reference value |
| `candidate_replacement` | Optional | A proposed current value (only when a deterministic match exists) |
| `evidence_source` | Required | What detection mechanism produced this finding |
| `classification` | Required | Category A/B/C/D/E from Section 3 |
| `confidence` | Optional | `HIGH` / `MEDIUM` / `LOW` / `UNKNOWN` — only when a replacement candidate exists and has measurable evidence quality |
| `blockers` | Required | List of reasons this finding cannot be auto-resolved (empty if unambiguous) |
| `recommended_disposition` | Required | `correct`, `regenerate`, `mark_unresolvable`, `re_export`, `ignore`, `manual_review` |
| `generated_at` | Required | ISO-8601 UTC timestamp |
| `revalidated_at` | Optional | When a recheck confirmed the finding is still current |

### Rationale for optionality

- `candidate_replacement` and `confidence` are absent when no plausible
  replacement exists (orphaned track_id with no surviving track row, or
  queue entry referencing a file that was permanently deleted).
- `revalidated_at` is absent on first generation; it is set when a
  subsequent re-scan confirms the finding is still active.
- `blockers` is never empty for `classification = A` or `classification = E`
  (those categories never get a correction action).

### Finding types (mapped from current surfaces)

| Finding type | Detected by | When |
|-------------|-------------|------|
| `cue_point_path_stale` | Compare `cue_points.filepath` against current `tracks.filepath` for the same file identity | Track was renamed/moved; cue row still points to old path |
| `playlist_track_path_stale` | Compare `set_playlist_tracks.filepath` against current resolved track paths | Set was built before a track rename |
| `crate_track_orphaned` | `manual_crate_tracks.track_id` has no matching row in `tracks` | Track was deleted from Library |
| `repair_queue_stale_path` | `metadata_repair_queue.relative_path` != current track's path (by track_id match) or track_id orphaned | Track was renamed or deleted |
| `review_snapshot_orphaned_track` | Review snapshot item's `track_id` has no matching `tracks` row | Track was deleted after review snapshot was created |
| `review_snapshot_stale_path` | Review snapshot item's `relative_path` != current track path | Track renamed after snapshot |
| `track_review_orphaned` | `track_reviews.track_id` has no matching `tracks` row | Track was deleted |
| `genre_review_snapshot_orphaned_track` | `genre_review_snapshots.items_json` item's `track_id` has no matching `tracks` row | Track was deleted after snapshot was created |
| `durable_finding_orphaned` | `quality_review_findings.track_id` has no matching `tracks` row | Track deleted |
| `provenance_orphaned` | `field_provenance.track_id` has no matching `tracks` row | Track deleted |
| `queue_path_stale` | Path string in a queue JSON/JSONL file does not resolve to an existing file | Track renamed/moved after queue entry was written |
| `bpm_anomaly_stale` | `bpm_anomalies.track_id` has no matching `tracks` row; or `filepath` differs from current track | Track renamed or deleted |
| `bpm_retry_pause_orphaned` | `bpm_retry_pauses.track_id` has no matching `tracks` row | Track deleted; pause is meaningless |
| `fingerprint_cache_orphaned` | `track_fingerprints.track_id` has no matching `tracks` row | Track deleted |
| `export_file_stale_path` | Path in an export file (M3U8/XML/JSON/CSV) does not resolve to an existing file | Track renamed after export |
| `historical_reference_stale` | Path or track_id in an immutable historical record (track_history, duplicate_groups, reconciliation_ledger, pipeline_runs, rolled-back rows) is stale | Track renamed or deleted after historical record was written |
| `cache_orphaned_or_stale` | track_id in a disposable cache (waveform_track_state, waveform_jobs, bpm_retry_pauses) is orphaned or its generation key is stale | Track deleted or cache key expired |

Classification-A and classification-E findings are emitted by detection (they
appear in the findings list with their artifact type, classification, and
`recommended_disposition = ignore`), but they are **never eligible for
mutation** and are excluded from all mutation-plan action proposals. The
`no_action_historical` and `no_action_cache` planned-action vocabulary entries
(Section 5) exist for plan-format completeness only; no future apply phase
executes them.

## 5. Action Vocabulary

Each action is a **plan-only proposal**. No action authorizes mutation; all
require review, revalidation, and explicit confirmation before a future apply
phase executes them.

### Core actions (for Category B — mutable authoritative/reference state)

#### `update_path_reference`

Update a path string in a mutable, non-historical artifact.

- **Applies to:** `cue_points.filepath`, `set_playlist_tracks.filepath`,
  queue JSON/JSONL entries (when the queue file format supports safe
  field-level mutation and the queue entry is not a historical snapshot)
- **Does NOT apply to:** `tracks.filepath` (already covered by current
  DB-only reconciliation), any Category-A historical row, JSON-blob fields
  inside review snapshots (those are Category C — regenerate, don't patch)
- **Fields:**
  - `action_id` (required)
  - `action_type`: `"update_path_reference"`
  - `artifact_type` (required)
  - `artifact_identifier` (required — exact row or entry locator)
  - `old_path` (required — absolute, root-contained)
  - `new_path` (required — absolute, root-contained, must exist on disk at revalidation time)
  - `evidence` (required — e.g., `same_track_id_different_path` for cues, `playlist_track_resolved_by_canonical_db` for set tracks)
  - `confidence` (required — HIGH/MEDIUM)
  - `blockers` (required — may be empty)
  - `reversibility` (required — `rollback_capable` or `regenerable`)

#### `rehome_track_id`

Update a track_id reference when the original track was superseded by a
known replacement track.

- **Applies to:** `manual_crate_tracks.track_id`,
  `field_provenance.track_id` (current rows only)
- **Preconditions:**
  - Old track_id has no surviving `tracks` row.
  - A new track_id exists that demonstrably represents the same audio file
    (same path that previously resolved to the old track_id, or a
    provenance trail showing the old track was renamed/promoted).
  - The artifact's non-reference fields (crate position, provenance
    value/origin/source) are unchanged.
- **Fields:** same structure as `update_path_reference`, plus
  `action_type`: `"rehome_track_id"`, `old_track_id`, `new_track_id`,
  `identity_evidence`.

### Notification/classification actions (for Category C — review state)

#### `regenerate_review_snapshot`

Signal that a review surface should be regenerated because its underlying
data has changed.

- **Applies to:** `metadata_repair_queue`, `enrichment_review_snapshots`,
  `beets_review_snapshots`, `duplicate_review_snapshots`,
  `quality_review_snapshots`, `bpm_anomalies`
- **Fields:**
  - `action_id` (required)
  - `action_type`: `"regenerate_review_snapshot"`
  - `artifact_type` (required)
  - `reason` (required)
  - `stale_reference_count` (required)
  - `blockers` (may be empty — user may need to decide whether to
    regenerate before reviewing existing decisions)

#### `mark_durable_finding_unresolvable`

Update a `quality_review_findings` row that references a deleted track.

- **Applies to:** `quality_review_findings` with orphaned `track_id`
- **Fields:**
  - `action_id` (required)
  - `action_type`: `"mark_durable_finding_unresolvable"`
  - `finding_id` (required)
  - `orphaned_track_id` (required)
  - `reason` (required)

### Regeneration actions (for Category D — exports)

#### `flag_export_for_regeneration`

Signal that a generated export file contains stale paths and should be
re-exported from current crate + tracks state.

- **Applies to:** all exported M3U8/JSON/CSV/XML files, staged Serato M3U8
- **Fields:**
  - `action_id` (required)
  - `action_type`: `"flag_export_for_regeneration"`
  - `export_path` (required — absolute, root-contained)
  - `export_format` (required)
  - `source_crate_id` (optional — known when the export was from a crate)
  - `stale_track_count` (required)

### No-op/ignore actions (for Categories A and E)

#### `no_action_historical`

Document that a stale reference is in immutable provenance and should not
be changed.

#### `no_action_cache`

Document that a stale reference is in a disposable cache and should be
ignored or handled by cache lifecycle.

## 6. Authority and Conflict Rules

### Canonical source of truth for track identity

The `tracks` table in `processed.db` is the single canonical source for
current track path identity. Every reference correction must resolve
against it.

### Resolution order

1. If `tracks.id` exists and `tracks.filepath` is a valid existing file →
   that path wins over any cached/snapshotted path.
2. If `tracks.id` exists but `tracks.filepath` does not exist → the track
   is in a missing-file state; do not propagate the stale path to other
   artifacts until the track's own path is reconciled (this is the existing
   DB-only reconciliation's job).
3. If `tracks.id` does not exist → the reference is orphaned.
   - If a replacement track can be proven (same path now owned by a new
     track_id after promotion), propose `rehome_track_id`.
   - Otherwise, the artifact's disposition depends on category: review
     state gets `mark_unresolvable`; mutable state gets a manual-review
     blocker.

### Conflict rules

- **Multiple candidate replacements:** Block — mark as `ambiguous` and
  require manual selection. Never auto-resolve.
- **Missing target:** Block — mark as `unresolvable` for review/durable
  state; require manual disposition for mutable state.
- **Candidate target outside selected root:** Block — refuse. This is a
  root-containment violation.
- **Inbox vs Library vs Quarantine zones:** A reference can validly point
  to any storage zone. Do not block zone transitions unless the target
  path is unreachable. A promotion from Inbox → Library that renames a file
  creates a stale reference in the Inbox path, which is exactly the
  scenario being corrected.
- **Historical/provenance records:** Never change. This is not a conflict
  to resolve; it is immutability to preserve. The finding model reports
  them as `classification = A` with `recommended_disposition = ignore`.
- **Target-current-provenance collision (field_provenance rehome):**
  Block — the `field_provenance` table enforces one current row per
  `(track_id, field_name)` via a partial unique index
  (`idx_field_provenance_current` WHERE `is_current = 1`). If the
  replacement track already has current provenance for the same
  `field_name`, the proposed `rehome_track_id` would produce a duplicate
  current row that violates the index. In this case the action must be
  blocked with a `target_current_provenance_collision` blocker. Manual
  resolution is required (e.g., compare both provenance histories and
  decide which to keep). Never silently overwrite or discard existing
  provenance.

### Fail-closed default

When evidence is ambiguous, the action must remain blocked. The default
disposition is `manual_review`. No auto-apply is authorized for any action
in this phase; that is a future implementation concern.

## 7. Plan / Review / Apply Separation

### Phase model

```
Detect (read-only findings)
  → Classify (assign artifact category, disposition)
  → Propose plan (specific actions with blockers and reversibility)
  → Human review (select, approve, reject, or defer each action)
  → Preview/revalidate (re-check every precondition at preview time)
  → Confirm (explicit `confirm=true`)
  → Apply (narrowly scoped reference mutation, one action at a time)
  → Verify (post-mutation checks)
  → Record provenance (ledger entry or artifact-specific ledger)
```

### Plan artifact

A plan is a dated JSON artifact persisted under
`<root>/logs/path_reconcile/`, with a filename distinguishing DB-only
plans from reference-artifact plans (e.g.,
`YYYYMMDD_path_reconcile_plan.json` for the existing DB-only plan;
`YYYYMMDD_reference_artifact_plan.json` for this phase). The plan contains:

- `generated_at`, `root`, `database`
- `finding_summary` — breakdown by artifact type and classification
- `planned_actions` — list of action dicts (each with action_id, type,
  artifact identifier, old/new values, evidence, blockers, reversibility)
- `limitations`
- `message` — clearly states "Plan only; no mutation has occurred."

### Why an artifact-specific ledger rather than extending the reconciliation_ledger

The current `reconciliation_ledger` table in `processed.db` is append-only
and carries `old_path` / `new_path` columns. It is tightly coupled to the
DB-only `update_path_reference` and `mark_stale_processed_state_path`
contract. A reference-artifact action may:

- mutate a column that is not a path (e.g., `track_id` → `track_id`)
- mutate a file on disk (JSON/JSONL queue entries)
- mutate a different database (`manual_crates.db`, `jobs.db`)

**Recommendation:** Each artifact domain records its own narrow rollback
data in a domain-specific way (e.g., a `manual_crates.db` before/after
snapshot for crate track rehome, a backup copy of a queue JSON file before
mutation), and each apply creates a new reference-artifact ledger entry in
a separate table (`reference_artifact_ledger` in `processed.db` or in a
purpose-built DB) that records the action identity, artifact, before/after
values, and rollback location — without forcing `old_path`/`new_path`
columns on artifacts that reference track IDs, not paths.

The current `reconciliation_ledger` remains the exclusive ledger for DB-only
tracks/processed_state path updates. This separation prevents schema
confusion and keeps the existing verified contract intact.

## 8. Revalidation and Stale-Plan Protection

A future executor must not trust a saved plan that has aged. Minimum
execution-time checks before any mutation:

### Plan-level checks

1. Selected root still matches the plan's recorded root.
2. Plan artifact file has not changed since it was loaded (sha256 identity).
3. `processed.db` and `manual_crates.db` (where applicable) still exist and
   are accessible.

### Action-level checks

4. The artifact (row, queue entry, export file) still exists.
5. The exact `old_value` (path or track_id) still matches the reviewed state.
6. The proposed `new_value` target still exists and validates:
   - For path targets: file exists on disk, is under the selected root.
   - For track_id targets: tracks row exists with a current filepath that
     resolves to an existing file.
7. No newer conflicting apply has occurred on the same artifact since the
   plan was created (check artifact-specific ledger or artifact
   modification timestamp).
8. The action remains unambiguous (no new candidates have appeared that
   would create ambiguity).
9. Current storage zone/reference semantics still match the reviewed plan
   (e.g., track is still in the expected storage zone).
10. All blockers recorded at plan time are still applicable; no new
    blockers have appeared.

### Artifact fingerprinting

For artifacts that support it:

- **SQLite rows:** Use `SELECT ... WHERE id=? AND <exact before values>`
  to verify no concurrent change (same pattern as current DB-only apply).
- **JSON/JSONL queue entries:** Compute a sha256 of the byte range before
  mutation (or of the entire file before mutation for small files).
- **Export files:** Compute a sha256 before flagging for regeneration
  (ensures the plan's understanding of what export content is stale hasn't
  changed).

## 9. Reversibility and Provenance

### By artifact class

| Class | Rollback strategy | Minimum before/after provenance |
|-------|-------------------|--------------------------------|
| Category A (immutable history) | N/A — never mutated | N/A |
| Category B — SQLite row (cue_points, set_playlist_tracks, field_provenance) | Must be rollback-capable: snapshot the exact row before mutation, write a new ledger entry with before/after values, support verified undo | `{table, row_id, before: {all columns}, after: {all columns}, plan_id, action_id, timestamp, backup_ref}` |
| Category B — queue JSON files | Must be rollback-capable: copy the file (or the specific entry range) to a backup location before mutation, hash-verify the backup | `{file_path, file_sha256_before, entry_location, before_entry, after_entry, backup_path, backup_sha256}` |
| Category B — manual_crate_tracks.track_id | Must be rollback-capable: snapshot the exact row, backup the crate DB | `{db_path, db_backup_path, table, row (crate_id, track_id, position), old_track_id, new_track_id}` |
| Category C (review state) | Safe to regenerate instead of rollback. Review decisions (`_decisions` tables) should be preserved across regeneration when the underlying track still exists. | N/A — regeneration is the preferred path |
| Category D (exports) | Safe to regenerate — re-export from current state | N/A |
| Category E (cache) | Dispose — no rollback needed | N/A |

## 10. API / Service Boundary Proposal

Prefer extending the existing reconciliation findings/plan/review concepts
rather than creating a parallel subsystem. The existing architecture already
provides:

- `GET /api/reconciliation/findings` — read-only evidence
- `POST /api/reconciliation/plans/propose` — plan artifact creation
- `POST /api/reconciliation/validate-plan` — plan validation
- `POST /api/reconciliation/apply/preview` — eligibility check
- `POST /api/reconciliation/apply` — confirmed DB-only apply
- `POST /api/reconciliation/ledger/{id}/rollback` — verified rollback

### Proposed future surface (minimal, additive)

| Endpoint | Purpose | Note |
|----------|---------|------|
| `GET /api/reconciliation/reference-findings` | Read-only detection of stale reference-artifact references (new finding types) | Extends the findings model; distinct from the current `findings` endpoint which covers DB/filesystem orphan detection |
| `POST /api/reconciliation/reference-plan/propose` | Propose a reference-artifact correction plan to disk | Same plan-artifact storage location, distinct filename pattern |
| `POST /api/reconciliation/reference-plan/validate` | Validate a saved reference-artifact plan | Mirrors existing validate-plan contract |
| `POST /api/reconciliation/reference-apply/preview` | Check eligibility of selected reference-artifact actions | Extends apply/preview pattern |
| `POST /api/reconciliation/reference-apply` | Confirmed apply of one reviewed reference-artifact action | One-action-per-request; confirm=true required |
| `POST /api/reconciliation/reference-ledger/{id}/rollback` | Verified rollback of a reference-artifact action | Extends rollback pattern |
| `GET /api/reconciliation/reference-ledger` | List reference-artifact ledger entries | Extends ledger listing |

### Service layer proposal

- `reference_findings_service.py` — read-only detection across all artifact
  surfaces inventoried in Section 2.
- `reference_plan_service.py` — proposal and validation (reuses the
  neutral `utils/path_reconciliation.py` where applicable for path-based
  detection, adds artifact-specific scanners for track_id-based surfaces).
- `reference_apply_service.py` — narrow, confirmed, verified apply with
  artifact-specific rollback mechanisms.

Do NOT create a parallel findings/plan/apply subsystem that duplicates the
existing reconciliation API structure. The reference-artifact endpoints
enumerate a different set of action types and operate on a wider set of
artifact surfaces, but they follow the same plan-first, review-gated,
single-action, verified-apply, rollback-capable contract already proven by
the current DB-only reconciliation.

### Stage 1 — Read-only detection and classification (smallest usable slice)

**Scope:**
- Implement `reference_findings_service.py` with scanners for Category A
  (immutable historical — classified, no action), B (mutable authoritative

- Tests 1–8 and 10–12 from Section 11 (detection + no-op + classification;

**Scope:**
- Implement `reference_plan_service.py`.
- Persist plan JSON artifacts alongside existing reconciliation plans.
- Extend plan validation with artifact-specific checks.
- Tests 13–16 (ambiguity/blocker).

**Risk:** Low. Plan-only; no mutation.

### Stage 3 — Apply preview with revalidation

**Goal:** `POST .../reference-apply/preview` that revalidates a selected
action against current state at preview time, surfacing any new blockers.

**Scope:**
- Implement preview logic in `reference_apply_service.py`.
- Revalidate all preconditions at preview time.
- Tests 17–18 (stale-plan protection).

**Risk:** Low. Preview is read-only; no mutation.

**Implemented contract (2026-08-12):** `POST
/api/reconciliation/reference-apply/preview` accepts one action ID plus an
exact saved plan artifact and matching plan ID. It reads the artifact once,
returns the snapshot SHA-256, and performs only read-only structural,
source-finding, artifact pre-state, canonical-target, and collision checks.
It introduces no reference-artifact apply, rollback, ledger, or writer.

### Stage 4 — Single-action apply (Category B artifacts only)

**Goal:** Confirmed apply of one reviewed reference-artifact correction at a
time, starting with the simplest, safest surfaces.

**Recommended order for apply implementation:**

1. `cue_points.filepath` update (simplest — single row, single column,
   already in `processed.db`).
2. `set_playlist_tracks.filepath` update.
3. `field_provenance.track_id` rehome.
4. `manual_crate_tracks.track_id` rehome (most complex — separate DB).

**Scope:**
- Implement `reference_apply_service.apply()`.
- Implement `reference_ledger` table and `reference_apply_service.rollback()`.
- Tests 19–23, 28–29.

**Risk:** Medium. Mutates authoritative reference state. Each artifact type
requires its own backup/rollback mechanism.

### Stage 5 — Review state regeneration notifications (Category C)

**Goal:** Enable flagging stale review snapshots for regeneration and
marking durable findings as unresolvable. No mutation of review data; just
notification and disposition tracking.

**Scope:**
- Implement regeneration-flag and mark-unresolvable actions.
- Ensure review decisions (`_decisions` rows for surviving tracks) are
  preserved when a snapshot is regenerated.
- Tests 24, 26.

**Risk:** Low. Classification and notification only.

### Stage 6 — Export stale-path detection (Category D)

**Goal:** Detect stale paths in export files and flag them in findings/plan.
No mutation of export files; re-export is a separate user action.

**Scope:**
- Extend reference findings to parse export files.
- Test 25.

**Risk:** Low. Read-only detection.

### Future high-risk milestone (separate design/review required)

**Filesystem move/rename/quarantine:** This is explicitly not part of the
reference-artifact reconciliation design. It requires:

- Its own design document with safety analysis.
- Hash-verified backups of files before any move/rename/quarantine.
- Explicit file-operation confirmation gates.
- Restoration paths for every operation.
- Zone-transition validation (Inbox → Library, Library → Quarantine).
- Protection of Inbox copies during workspace promotion.
- No overlap with MIK-authoritative data.

Do not attempt to fold filesystem operations into the reference-artifact
phases above.

## 13. Limitations

1. **JSON-blob fields.** Several review state tables store track references
   inside `items_json` / `groups_json` TEXT columns. This design does not
   attempt to surgically patch individual values inside serialized JSON
   blobs. Instead, stale review snapshots are flagged for regeneration so
   the owning service re-derives them from current track state. This
   respects the snapshot lifecycle model already used by enrichment_review,
   beets_review, duplicate_review, and quality_review services.

2. **`metadata_lookup_cache`** is keyed on (artist, title), not track or
   path, so it does not stale from renames. No action needed.

3. **Waveform cache.** Waveform artifacts are named by a stat-signature
    generation key (library/track identity; size, mtime, ctime, device,
    inode; schema/algorithm settings), never by a source-content hash or
    path. A rename/move alone does not stale that signature. Cache lifecycle
    (eviction/pruning) handles stale entries; reconciliation does not.

4. **`processed_state` historical rows.** The current
   `mark_stale_processed_state_path` action already handles active
   processed_state rows. Historical stale rows (already `status='stale'`)
   are intentionally left as-is.

5. **`bpm_anomalies`** lives in `jobs.db`, not `processed.db`. Its
   `filepath` column is a snapshot at detection time. A stale anomaly
   should be handled by re-running BPM anomaly detection, not by
   reconciliation.

6. **Multi-track references.** The duplicate_review `groups_json` may
   reference multiple track_ids in a single group entry. This design treats
   groups as a single regeneration unit — if any member track_id is
   orphaned, the entire snapshot should be regenerated.

7. **Delete-or-rehome boundary.** When a track is deleted and no
   replacement track exists, the only safe action is to mark the reference
   as unresolvable (for Category B) or regenerate (for Category C). This
   design does not propose deleting orphaned references automatically.

8. **`tag_write_operations`** in `jobs.db` stores `track_id` and
   root-relative `relative_path` fields inside serialized JSON columns
   (`plan_json`, `backup_manifest_json`, `result_json`). A rename or
   promotion can stale those references, but these rows are **immutable
   operational provenance**: they document a specific point-in-time
   controlled tag-write operation — what was planned, which track/path,
   the hash-verified backup identity, and the verified write result. The
   `backup_manifest_json` entries reference backup files under
   `backend/data/tag_write_backups/<operation_id>/` that are the
   authoritative restore source for that operation; those backup paths
   are similarly immutable. Like all Category-A artifacts, these rows are
   detected and classified by the finding model but **never rewritten**.
   Stale references here are evidence of what happened at the time the
   operation was executed.
